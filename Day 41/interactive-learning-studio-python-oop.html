01

Classes and objects: from scattered variables to meaningful models

The foundation. If this part feels vague, the rest becomes fake confidence with fancy words.

Unlocked

Detailed explanation

In procedural code, you often juggle loose variables: student_name, student_grade, student_id. That works until related data and behavior start drifting apart. A class gives you a blueprint. An object is one concrete instance built from that blueprint. In Python, classes let you bind data and behavior together so the code starts modeling the real thing instead of just storing fragments.

Think of a class as a cookie cutter and an object as an actual cookie. The cutter defines shape; each cookie has its own chocolate chips, cracks, and tiny imperfections. Same structure, different state.

Comparison: dictionary vs class

Dictionary approach 
student = {
    "name": "Mira",
    "grade": 92,
    "email": "mira@example.com"
}

Fast for simple data. Falls apart when you need validation, behavior, or lots of similar records.

Class approach 
class Student:
    def __init__(self, name, grade, email):
        self.name = name
        self.grade = grade
        self.email = email

    def is_honors(self):
        return self.grade >= 90

Better when the thing has identity and behavior, not just fields.

Topic-specific example

class BankAccount:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self.balance = balance

    def deposit(self, amount):
        self.balance += amount

    def withdraw(self, amount):
        if amount <= self.balance:
            self.balance -= amount
        else:
            print("Insufficient funds")

account = BankAccount("Hulk", 150)
account.deposit(50)
account.withdraw(80)
print(account.balance)  # 120

Notice the win: the account knows how to change itself. You don’t need random functions elsewhere mutating balance with zero guardrails.

Diagram: blueprint to instance

A class defines structure and behavior. Each object carries its own state while sharing methods.

Practical exercise

Create a Book class with title, author, and pages. Add a method called is_long_read() that returns True if the book has more than 300 pages.

Stretch task: add a description() method that returns a readable sentence, not just raw data.

Common misconceptions

"A class is just a fancy dict."

Nope. A dict stores data. A class can enforce rules and express behavior.

"Everything should be a class."

Absolutely not. Tiny scripts and simple transformations often work better with plain functions.

"__init__ creates the object."

Technically, it initializes an already created object. Useful distinction once you hit advanced Python.

Key takeaways

Classes are blueprints
Objects store state
Methods express behavior
Use classes for meaningful models

02

Encapsulation and state: keep objects valid, or pay for it later

OOP gets useful when your objects defend their own integrity instead of trusting every caller not to be messy.

Locked
Pass Module 1 first. Otherwise you’re stacking jargon on a shaky base.

Detailed explanation

Encapsulation means bundling data with the methods that control access to it. In plain English: the object owns its state, and other code should interact through safe interfaces. Python does not enforce privacy like Java or C++, but it gives you conventions and tools such as leading underscores and @property.

Imagine a vending machine. You do not reach into the machine and manually rearrange coins and snacks. You press buttons and insert money through approved interfaces. That’s encapsulation. The machine protects its internal rules.

Topic-specific example

class Temperature:
    def __init__(self, celsius):
        self.celsius = celsius

    @property
    def celsius(self):
        return self._celsius

    @celsius.setter
    def celsius(self, value):
        if value < -273.15:
            raise ValueError("Temperature cannot go below absolute zero")
        self._celsius = value

    def to_fahrenheit(self):
        return (self.celsius * 9/5) + 32

Without validation, any code could set celsius = -999 and your object becomes nonsense. Encapsulation keeps garbage out.

Diagram: safe interface vs direct mutation

Comparison: public free-for-all vs controlled access

Bad pattern 
player.health = -500
player.level = "wizard king"

Any caller can wreck the state. Congrats, your game logic is now fan fiction.

Better pattern 
player.take_damage(20)
player.level_up()

State changes happen through methods that preserve rules.

Practical exercise

Build a Wallet class with a private-ish _balance attribute. Add methods for deposit(), spend(), and a read-only property for balance. Prevent spending more than the wallet contains.

Common misconceptions

"Python has no private attributes, so encapsulation doesn't matter."

Wrong. Conventions plus properties still give you control and clarity.

"Getters and setters everywhere is good design."

No. That often just recreates public access with extra ceremony.

"Underscore means impossible to access."

It means "hands off unless you know why." Python trusts adults, sometimes too much.

Key takeaways

Protect object invariants
Use methods for state changes
@property enables validation
Conventions matter in Python

03

Inheritance and polymorphism: useful power, abused constantly

This is where people either become elegant or start building inheritance spaghetti with delusions of architecture.

Locked
Pass Module 2 first. Earn your abstractions.

Detailed explanation

Inheritance lets one class reuse and extend another. A child class inherits attributes and methods from a parent class. Polymorphism means different objects can respond to the same method call in their own way. That lets you write more general code without giant if type == ... messes.

Analogy: a music conductor can gesture "play" to strings, brass, and percussion. They all respond to the same instruction, but each section behaves differently. Same interface, different implementation. That's polymorphism.

Topic-specific example

class Animal:
    def speak(self):
        raise NotImplementedError("Subclasses must implement speak")

class Dog(Animal):
    def speak(self):
        return "Woof"

class Cat(Animal):
    def speak(self):
        return "Meow"

def make_it_speak(animal):
    print(animal.speak())

for pet in [Dog(), Cat()]:
    make_it_speak(pet)

The function doesn’t care whether it gets a Dog or a Cat. It only cares that the object honors the expected behavior.

Diagram: shared interface, specialized behavior

Comparison: polymorphism vs type-checking soup

Brittle approach 
if animal_type == "dog":
    bark()
elif animal_type == "cat":
    meow()
elif animal_type == "cow":
    moo()

Every new type forces you to reopen and edit old logic. That gets ugly fast.

Polymorphic approach 
for animal in animals:
    animal.speak()

Cleaner, extensible, and less annoying to maintain.

Practical exercise

Create a base class called Notification with a send() method. Then make EmailNotification and SMSNotification subclasses that implement send() differently. Write a function that sends any notification object.

Common misconceptions

"Inheritance is always the best way to reuse code."

No. Composition is often safer and more flexible.

"Polymorphism requires inheritance."

Not in Python. Duck typing says if it behaves correctly, that's enough.

"More hierarchy means better architecture."

Usually the opposite. Deep inheritance trees are where maintainability goes to die.

Key takeaways

Reuse shared behavior carefully
Override methods intentionally
Polymorphism reduces branching
Shallow hierarchies beat deep ones

04

Composition and design judgment: build systems that survive contact with reality

Real mastery is not "can I use OOP?" It’s "should I, and what shape should it take?"

Locked
Pass Module 3 first. No skipping to the part where you pretend to be senior.

Detailed explanation

Composition means building objects from other objects instead of inheriting everything. It follows the idea "has-a" instead of "is-a". A Car has an Engine. A Course has Lessons. This often leads to designs that are more modular and easier to change.

Analogy: a sports team is not a special type of coach. It contains players, a coach, a strategy, and support staff. Forcing those relationships into inheritance would be ridiculous. Composition matches reality better.

Topic-specific example

class Engine:
    def start(self):
        return "Engine started"

class Car:
    def __init__(self, engine):
        self.engine = engine

    def drive(self):
        return f"{self.engine.start()} and car is moving"

engine = Engine()
car = Car(engine)
print(car.drive())

This is cleaner than making Car inherit from Engine, which would imply a car is an engine. It obviously isn’t. Bad inheritance usually starts by lying about relationships.

Diagram: composition over inheritance

Comparison: when to use what

Inheritance fits when
  • There is a real is-a relationship
  • Subclasses meaningfully share an interface
  • The hierarchy stays shallow and stable
Composition fits when
  • Objects combine capabilities
  • Behavior should be swappable
  • You want looser coupling and easier testing

Practical exercise

Design a Playlist class that contains multiple Song objects. Add methods to add songs, calculate total duration, and list song titles. Then ask yourself: would inheritance help here? It shouldn’t.

Common misconceptions

"Composition is advanced, inheritance is normal."

Backwards. Composition is often the safer default.

"Good OOP means using all four pillars everywhere."

That’s textbook cosplay. Good design solves the problem cleanly.

"If I can make it a class hierarchy, I should."

That impulse creates rigid systems. Resist it.

Key takeaways

Prefer truth in relationships
Composition is often the default
Use inheritance sparingly
Design for change, not theory

Summary notes
