01
Planning

Define the Agent's Mission & Scope

⏱ 2–4 hrs
Objectives
  • Write a one-sentence mission statement the agent must accomplish autonomously.
  • Decide the boundary between what the agent decides and what a human must approve.
  • List the real-world tools/APIs the agent will need access to.
  • Define what "task complete" and "task failed" look like, concretely.
Tasks
Prompt examples
Act as a staff AI engineer. I'm scoping an autonomous agent that [does X for Y users]. Given these 5 example requests: [...], draft (1) a one-sentence mission statement, (2) the minimum tool list required, (3) three failure modes I should guard against.
Here is my agent's mission statement: "[...]". Stress-test it — list edge-case requests that are ambiguous about whether the agent should act autonomously or ask a human first.
Best AI tools
ToolUse
Claude (Opus)Long-context reasoning to pressure-test scope and edge cases Recommended
ChatGPT (o-series)Fast brainstorming of failure modes and user stories Alternative
Notion AI / Coda AITurn scope notes into a living PRD teammates can edit

Why Claude here: scoping needs the model to hold your whole product context, example requests, and constraints at once and reason about contradictions — that favors strong long-context reasoning over speed.

Expected output
A one-page agent brief: mission statement, autonomy level, tool list, hard constraints, and 5–10 example tasks.
Efficiency tipWrite the failure modes before the happy path — it's the fastest way to discover the agent needs a human approval gate you hadn't planned for.
Best practices
✓Scope to one job the agent does end-to-end, not five jobs it does halfway.
✓Write success criteria as something you could grade automatically later (this becomes your eval set in Waypoint 06).
Common mistakes
✗Scoping "a general assistant" instead of a specific, bounded workflow — this is the single biggest cause of agents that never ship.
✗Skipping the autonomy-level decision, which surfaces later as a security or trust incident instead of a design choice.

02
Planning

Architecture & Tool Design

⏱ 4–8 hrs
Objectives
  • Choose the control pattern: single ReAct loop, planner+executor, or supervisor with sub-agents.
  • Design each tool as a precise function signature the model will call.
  • Decide what state/memory persists between steps and between sessions.
  • Draw the architecture so a teammate could implement it without you.
Tasks
Prompt examples
I'm designing an agent with this mission: [paste brief]. Propose a control-loop architecture (ReAct vs plan-and-execute vs supervisor+sub-agents) with tradeoffs specific to my use case, and recommend one.
Here are the tools my agent needs: [list]. Write clean function signatures with typed parameters and docstrings good enough for an LLM to call correctly on the first try.
Best AI tools
ToolUse
Claude (Opus/Sonnet)Architecture reasoning + tool-schema writing Recommended
Eraser.io (DiagramGPT)Text-to-diagram for the control-flow chart
Excalidraw + AI pluginFast whiteboard-style architecture sketching Alternative

Why Claude here: tool-schema design is really an interface-design problem in disguise — the model needs to critique ambiguity in parameter names the way it would review an API, which rewards careful instruction-following.

Expected output
An architecture diagram, a finalized tool list with function signatures, and a written memory strategy.
Efficiency tipStart with the fewest tools that can complete your example tasks from Waypoint 01. Every extra tool multiplies the ways the agent can pick the wrong one.
Best practices
✓Name tools by outcome (search_order_status), not by implementation (call_api_endpoint_3).
✓Give every tool a maximum blast radius — a read-only tool and a destructive tool should never share a name pattern.
Common mistakes
✗Designing 20+ tools upfront "to be safe" — this is the top cause of the model calling the wrong tool.
✗No loop-termination policy, so a stuck agent burns tokens (and money) in an infinite retry loop.

03
Setup

Framework & Model Selection

⏱ 2–3 hrs
Objectives
  • Choose an orchestration framework (or decide to hand-roll the loop).
  • Choose the reasoning model, and a cheaper fallback model for simple steps.
  • Confirm the framework supports your chosen control pattern from Waypoint 02.
Tasks
Prompt examples
Compare LangGraph, CrewAI, and a hand-rolled ReAct loop for an agent that [mission]. I need [multi-agent / single-agent], [stateful memory / stateless], deployed on [platform]. Recommend one and justify it against my constraints, not in general.
Write a minimal working example in [LangGraph/CrewAI/Claude Agent SDK] with one tool call, so I can confirm my environment is wired correctly before building the real agent.
Best AI tools
ToolUse
Claude Agent SDK / MCPNative tool-use + Model Context Protocol for tool interop Recommended
LangGraphGraph-based control for complex branching/looping agents Alternative
CrewAI / AutoGenMulti-agent collaboration patterns out of the box
Claude Code / CursorScaffold the boilerplate for whichever framework you pick

Why this pairing: MCP standardizes how tools are described and called, so switching or adding tools later doesn't mean rewriting your agent's core loop.

Expected output
A working "hello world" agent that calls one real tool end-to-end, plus a documented model choice.
Efficiency tipRoute trivial sub-steps (formatting, extraction) to a smaller/cheaper model and reserve your best model for planning and tool selection — this alone can cut agent run cost by half.
Best practices
✓Prototype the smallest possible working loop before adding your real tools.
✓Pin framework and model versions in your repo — agent behavior is version-sensitive.
Common mistakes
✗Choosing a heavyweight multi-agent framework for a single-purpose agent, adding orchestration overhead you don't need.
✗Picking the most powerful model for every step instead of only where reasoning quality actually matters.

04
Build

Build the Core Reasoning Loop

⏱ 1–2 days
Objectives
  • Implement the observe → think → act → observe loop.
  • Write the system prompt that defines the agent's role, constraints, and tool-use rules.
  • Add step limits, retries, and a clean "stuck" exit path.
Tasks
Prompt examples
Write a system prompt for an autonomous agent whose mission is [X]. It has access to these tools: [list]. It must ask for human approval before [Y], never do [Z], and stop after [N] steps if it hasn't finished. Output the prompt only.
Here's my agent's step log for a failed run: [paste log]. Diagnose where the reasoning broke down — wrong tool choice, misread tool output, or premature termination — and suggest a system-prompt fix.
Best AI tools
ToolUse
Claude CodeWrites and iterates on the loop implementation with you Recommended
Cursor / GitHub CopilotIn-editor pair programming for the same task Alternative
LangSmithTrace every step of the loop while you debug it live

Why Claude Code here: this stage is iterative debugging of agent reasoning, not one-shot code generation — you want a coding agent that can read its own trace logs and propose fixes in context.

Expected output
A running agent loop that completes at least 6/10 of your example tasks unassisted, with full step logs.
Efficiency tipLog the raw tool inputs/outputs, not just a summary — most reasoning bugs are the agent misreading a tool's actual response shape.
Best practices
✓Keep the system prompt as short as it can be while still being unambiguous — verbose prompts get partially ignored.
✓Make tool outputs the agent sees structured (JSON), not prose, so re-planning is reliable.
Common mistakes
✗No step cap — a single ambiguous instruction can loop the agent indefinitely and rack up API cost.
✗Testing only the happy path before moving to Waypoint 05, hiding bugs that surface later as "flaky" tool calls.

05
Build

Tool Integration & Function Calling

⏱ 2–4 days
Objectives
  • Wire each designed tool to a real API, database, or service.
  • Handle tool errors so the agent can recover instead of crashing.
  • Add permission checks for any tool with side effects.
Tasks
Prompt examples
Here's my tool function: [paste code]. Rewrite its error handling so that failures return a structured, LLM-readable message explaining what went wrong and what the agent could try next.
Generate unit tests for this tool function covering: valid input, missing required field, upstream API timeout, and malformed API response.
Best AI tools
ToolUse
ComposioPre-built, auth-handled connectors to 100+ SaaS tools Recommended
MCP serversStandardized tool interfaces you can swap in/out Recommended
Zapier / Make AINo-code glue for simpler integrations Alternative
Postman AIGenerate and test API request schemas quickly

Why Composio/MCP here: hand-writing auth and error handling for every third-party API is the slowest part of this stage — pre-built connectors remove that entirely for common tools.

Expected output
All tools live-tested against real endpoints, with error paths that return usable feedback to the agent instead of crashing the run.
Efficiency tipWrite the tool's error message as if you were writing it for the agent, not for a human developer — "no results for query, try broadening it" beats a raw 404.
Best practices
✓Treat every tool boundary as untrusted input — validate before executing, especially for anything with write access.
✓Version and log every tool call in production the same way you did in development.
Common mistakes
✗Letting raw exceptions bubble up to the agent — it can't reason about a Python traceback.
✗No confirmation gate on destructive tools, which turns one bad plan into a real-world incident.

06
Validate

Testing, Evaluation & Guardrails

⏱ 2–3 days
Objectives
  • Turn your example tasks into a repeatable evaluation set.
  • Score trajectories, not just final answers — did it use the right tools, in a reasonable number of steps.
  • Add guardrails for prompt injection, scope creep, and unsafe tool calls.
Tasks
Prompt examples
Given this agent mission and tool list: [...], generate 30 evaluation tasks: 15 typical, 10 edge-case, 5 adversarial (attempting prompt injection or asking for out-of-scope actions).
Here is a full agent trajectory (thoughts, tool calls, results, final answer): [paste]. Grade it 1–5 on tool-choice correctness, efficiency of steps, and final-answer accuracy. Explain each score.
Best AI tools
ToolUse
LangSmithTrajectory tracing + eval dataset management Recommended
BraintrustEval scoring pipelines with human + LLM graders Alternative
Weights & Biases WeaveExperiment tracking across prompt/model versions
Claude (as grader)LLM-as-judge scoring for subjective quality

Why trace-first tools here: agent bugs are almost always in the middle of a trajectory, not the final answer — you need step-by-step visibility, not just pass/fail.

Expected output
A versioned eval set with a baseline pass rate, plus a guardrail layer that blocks or escalates unsafe requests.
Efficiency tipRe-run the full eval set on every meaningful change — agents regress in surprising places when you fix one prompt issue.
Best practices
✓Grade the trajectory (tool choices, step count), not only whether the final answer looks right.
✓Include tool outputs that look like instructions in your adversarial tests — that's the real-world injection vector.
Common mistakes
✗Evaluating manually by eyeballing a handful of runs instead of a fixed, repeatable eval set.
✗No adversarial testing, so the first prompt injection attempt happens in production.

Execution

Deployment, Monitoring & Iteration

⏱ 1–2 days + ongoing
Objectives
  • Ship the agent behind a stable interface (API, chat, or scheduled job).
  • Monitor cost, latency, and trajectory quality in production.
  • Build a feedback loop from real runs back into your eval set.
Tasks
Prompt examples
Write a Dockerfile and minimal deployment config for a Python agent service using [framework], exposing a single /run endpoint, deployable to [Fly.io/Modal/AWS].
Here are this week's production failure logs: [paste]. Cluster them into failure categories, rank by frequency, and suggest which one to fix first.
Best AI tools
ToolUse
Modal / Fly.ioFast deploy for Python agent services Recommended
Helicone / LangSmithProduction tracing, cost, and latency monitoring
Docker + AWS/GCPFull control for larger-scale deployments Alternative
DatadogUnified alerting alongside existing infra

Why this pairing: agent cost and failure patterns shift once real users hit it — you need cheap, fast redeploys plus per-run tracing from day one, not bolted on later.

Expected output
A deployed agent with live dashboards, alerting on step-limit and guardrail events, and a weekly eval-refresh habit.
Efficiency tipTreat every production failure as a candidate new eval case — this is the cheapest way to keep the agent improving after launch.
Best practices
✓Ship behind a feature flag or limited rollout before opening the agent to all users.
✓Track cost per completed task, not just total spend — it's the metric that actually tells you if the agent is worth running.
Common mistakes
✗Deploying with no monitoring, so the first sign of trouble is a user complaint.
✗Treating launch as the finish line instead of the start of the feedback loop.

Debrief

Workflow summary

This route takes an autonomous, tool-using agent from a one-sentence mission statement to a monitored production service in seven waypoints: scope it, architect it, choose the stack, build the reasoning loop, wire up real tools, prove it works against an eval set, then ship and watch it. Each waypoint hands the next one a concrete artifact — brief → diagram → working stub → running loop → live tools → passing eval → dashboard.

Future automation opportunities

Where this workflow itself can be automated further once the agent is stable in production.

  • ↻Self-healing tool errors
    Auto-retry failed tool calls with an LLM-rewritten input before surfacing the failure to a human.
  • ⌘Auto-generated eval sets
    Turn sampled production trajectories into new eval cases automatically each week.
  • ₵Cost-based model routing
    Route each step to the cheapest model that historically succeeds at that step type.
  • ◎Supervisor-of-agents
    Add a lightweight supervisor that spins up specialized sub-agents only when a task needs them.
